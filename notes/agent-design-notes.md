# 个人网站的 Agent 设计

> 学习笔记 · 2026 年 6 月 1 日

---

## Agent 目标

做一个**数字分身 Agent**，嵌入个人网站，让访问者可以直接通过对话了解张强。

**目标用户**：HR（招聘方）、潜在合作伙伴。

**核心场景**：访问者不需要一篇篇翻文章，而是可以直接问：

- "你怎么看 GEO 的未来？"
- "讲一个你在百度做过的复杂项目"
- "你和其它 AI 产品经理有什么不同？"

Agent 基于张强所有公开的思考、案例、经历，给出**有逻辑、有温度**的回答。

**差异化定位**：这个数字分身本身就是产品思维的最好展示——就连这个分身本身，也是张强设计的产品。

## 核心 RAG 架构

### RAG 是什么

RAG（检索增强生成，Retrieval-Augmented Generation）是一种让 LLM 基于外部知识库回答问题的技术模式。

### 为什么需要 RAG

LLM 的训练数据有截止日期，且不知道你的个人经历。RAG 的核心思路是：**在提问之前，先把相关知识"喂"给 LLM**，让它基于这些材料来回答。

### 完整流程

```
用户提问
    ↓
[1. 向量检索]  把问题转成向量 → 在知识库中找最相关的 N 段内容
    ↓
[2. 组装 Prompt]  把检索到的内容 + 用户问题 + System Prompt 拼在一起
    ↓
[3. LLM 生成]  将组装好的 Prompt 发给 LLM，生成回答
    ↓
返回回答给用户
```

### 不需要的东西

- **不需要意图识别规则**：现代 LLM 本身有很好的意图理解能力，不需要手写 if-else 规则。
- **不需要工作流引擎**：问答场景是单轮/多轮对话，RAG 就够了。工作流是 V3 的事情。

### 需要设计的东西

- **System Prompt（人格定义）**：定义 Agent 的语气、风格、边界
- **检索策略**：每次检索几条最相关的内容
- **对话历史管理**：记住上下文，支持追问

## 知识库存储方案

### 为什么需要向量化存储

关键词匹配只能找到字面相同的词，无法理解语义。

```
用户问："你怎么看 GEO 的未来？"

关键词匹配 → 只找到标题或正文里明确写了"GEO"和"未来"的文章
语义向量检索 → 能匹配到"GEO 行业格局"、"趋势判断"等相关内容
                 即使文章里根本没有"未来"两个字
```

### 向量化存储的原理

```
你的 markdown 文件
       ↓ 用嵌入模型转换
  一串数字（向量），比如 [0.023, -0.451, 0.789, ...] × 1536 维
       ↓ 存到向量数据库
  用户提问 → 问题也转成向量 → 和库里的向量算"距离"
       ↓
  距离最近的 = 语义最相关的
```

### 三种向量数据库方案

| 方案 | 技术 | 优点 | 缺点 |
|------|------|------|------|
| A. 专用向量数据库 | Chroma | 开箱即用、免费开源、Python 原生 | 需要自己部署管理 |
| B. 托管向量服务 | Pinecone / Supabase | 免运维、数据不丢 | 收费、多一个外部依赖 |
| C. 数据库插件 | PostgreSQL + pgvector | 生产级成熟稳定 | 部署复杂度最高 |

**本项目选择方案 A（Chroma）**：内容量不大（几十篇文章 + 几段介绍），Chroma 完全够用，且最简单。

## 向量化的切片策略

### 什么是切片

把长文档切成小块，每块转成一个向量存起来。切片质量直接影响检索质量。

### 为什么切片是重要的设计决策

切片太粗 → 检索精度低，返回一堆不相关的内容
切片太细 → 语义不完整，关键信息被拆散
切错位置 → 本该在一起的信息被拆到两个切片里

**切片的本质不是技术问题，是信息架构问题。**

### 三种切片策略

#### 策略 1：固定长度切片

每 N 字切一刀，不管内容结构。

- **适用**：长篇小说、新闻流水账
- **不适用**：你的任何内容（文章有逻辑结构，必然切坏）

#### 策略 2：按标题层级切片（结构感知）

以 `##` 二级标题为切片边界，每个二级标题下的内容是一个独立切片。

```
原文结构：
# GEO 行业格局分析
## 一、四类服务商（500 字）
## 二、两端一连接框架（800 字）
## 三、未来趋势判断（600 字）

切出来：
  切片 1: "## 一、四类服务商" + 500 字  ← 语义完整
  切片 2: "## 二、两端一连接框架" + 800 字  ← 语义完整
  切片 3: "## 三、未来趋势判断" + 600 字  ← 语义完整
```

- **优点**：每个切片语义完整，标题本身提供上下文
- **缺点**：如果某个标题下内容过长（2000+ 字），切片太大影响检索精度

**这是本项目的主力策略**——文章结构清晰、标题完整。

#### 策略 3：递归语义切片

将文本递归地分成小块，每次在"语义最不相关"的地方下刀。分隔符优先级：

```
段落分隔（两个换行）> 单换行 > 句号 > 逗号 > 空格
```

- **适用**：无结构的自由文本
- **不适用**：需要严格结构的场景

### 本项目采用的混合策略

| 内容类型 | 切片策略 | 粒度 | 原因 |
|----------|---------|------|------|
| 文章 | 按 ## 标题切 | 每段 500-1500 字 | 文章结构好，标题边界就是语义边界 |
| 项目经历 | 一个项目 = 一个切片 | 每段 200-500 字 | 每个项目独立成意 |
| 自我介绍/FAQ | 按 Q&A 对切 | 每对 100-300 字 | 问答本身就是天然边界 |

### 重叠窗口

在相邻切片之间设置 100 字左右的重叠区，防止边界处信息丢失。

## 切片效果验收

### 人工抽查（定性）

准备 10 个典型问题，手动验证：

```
1. 每个问题 → 跑检索 → 看返回了哪些切片
2. 判断标准：
   ✓ 切片内容能完整回答这个问题 = 切得好
   ✗ 切片内容缺关键信息，明显在另一个切片里 = 切坏了
   ✗ 切片内容混杂了不相关的内容 = 切得太粗
```

### 脚本验证（定量）

写验证脚本跑以下指标：

1. **切片数量分布**：有没有过长（>2000 字）或过短（<50 字）的切片？
2. **专属匹配率**："怎么看 GEO 未来？" 是否主要匹配到 GEO 文章，而非自我介绍？
3. **相关性打分**：用 LLM 给每个检索结果打 1-5 分

## PM 需要掌握到什么程度

```
层次 4: 自己写切分算法、调嵌入模型参数     ← 工程师的事，不需要
──────────────────────────────────────
层次 3: 理解三种切片策略的适用场景和边界   ← 需要到这个层次
──────────────────────────────────────
层次 2: 知道"切片会切坏语义"这件事存在    ← 已掌握
──────────────────────────────────────
层次 1: 不知道有切片这回事               ← 已跨越
```

**产品经理的深度到"能判断好坏"就够了**——判断切片是否语义完整，判断检索结果是否相关，判断 Agent 回答是否准确。这本质上和"判断产品功能是否解决用户问题"是一样的能力。

## 产品经理的设计空间

在 RAG 系统中，产品经理的价值不在技术实现，而在这些设计决策：

| 设计决策 | 说明 |
|----------|------|
| Agent 人格 | 用什么语气？有什么边界？有什么招牌回答？ |
| 知识库范围 | 包含什么内容？不包含什么？ |
| 切片策略 | 不同类型的内容用什么切法？ |
| 检索精度 | 每次返回几条内容？重叠多少？ |
| 回答质量 | 回答太短/太长/太偏/编造？怎么调整 Prompt？ |
