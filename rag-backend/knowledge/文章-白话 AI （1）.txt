# RAG 是什么，有什么用途
> RAG 全名 Retrieval（检索）Augmented（增强）Generation（生成），检索增强生成技术。
> 是结合了信息检索和语言生成的技术，当模型需要回答问题的时候，它会先从一个文档集合中，检索出相关的信息，然后利用这些检索到的信息来指导文本生成，从而提高预测的质量和准确性。

## 为什么需要有 RAG 技术
RAG 的出现主要为了解决通用大模型在实际落地应用中的几个核心痛点：
- 静态知识的局限：大模型训练完成后，其知识库就固定了，训练模型的数据是固定的、历史的，对于实时更新的信息（如新闻、股价）或企业内部未公开的私有知识，模型无法获取。
- 模型的幻觉问题：大模型有时会生成看似合理但不符合事实的 “幻觉” 答案，需要外部资料帮助模型验证生成内容的合理性。
- 落地专业领域下的模型可用性：通用大模型的训练数据赋予了它通用的逻辑理解与回答能力，但不具备行业专业性。想让大模型精通某个专业领域（如法律、医疗），传统方法需要耗费大量算力和数据对模型进行 “微调”，成本高且可能导致原有能力遗忘。

## RAG 技术的原理
简单理解就是在问模型问题时，给模型一段文档，让模型参照这个文档回答问题。
- 当需要给模型的文档越来越长、越来越多时，模型难以高效查找，随即衍生出文档切片（chunking）技术。切片后对每一小段文字进行embedding（向量化）（通过某个模型），将切片后的文字转化为一个个多维坐标数字。用户的问题也会转为向量坐标数字，根据坐标的远近，模型找到对应的切片内容，再将用户的问题与检索到的内容一起给到模型，由模型生成回答。
- 将切片后的内容向量化后，需要进行向量存储，即将文字内容与向量坐标对应起来并存入向量数据库。传统数据库是ID+内容，向量数据库是向量坐标（数组）+内容。
- RAG 的关键是内容的处理压缩（即切片→向量化），但这种切片技术也存在缺陷：可能会因为模型对内容的理解不够充分导致切片位置错误，或在压缩过程中丢失重要内容（切片损失）。
总结来说，**RAG 技术的流程是：将文档【切片】→【编码（向量化）】→【存储】，文档内容通过以上 3 步存储在向量数据库中等待检索。当用户提出问题时，先将问题用同样的 embedding 模型进行向量化，然后从向量数据库中找到位置相近的内容，最后把问题和挑选出的内容一起给到模型生成答案。**

## RAG技术的弊端
将文档切片向量化后，不可避免的会损失文本的全局结构、实体间的复杂关系和深层的逻辑链条，模型检索到的可能只是“语义相近”的片段，对于全局问题和局部片段的问题匹配度太低；
在做设计RAG结构时，其中重点就是**设计向量化的切片策略**
切片太粗 → 检索精度低，返回一堆不相关的内容
切片太细 → 语义不完整，关键信息被拆散
切错位置 → 本该在一起的信息被拆到两个切片里
**切片的本质不是技术问题，是信息架构问题。**
### 三种切片策略
- 策略 1：固定长度切片，每 N 字切一刀，不管内容结构。
    - **适用**：长篇小说、新闻流水账
    -  **不适用**：内容围绕某个主题，上下文有语义关联的内容；
- 策略 2：按标题层级切片（结构感知），以 `##` 二级标题为切片边界，每个二级标题下的内容是一个独立切片。
>  比如原文结构：
>  GEO 行业格局分析
> ## 一、四类服务商（500 字）
> ## 二、两端一连接框架（800 字）
> ## 三、未来趋势判断（600 字）
切出来
>  切出来：
> 切片 1: "## 一、四类服务商" + 500 字  ← 语义完整
> 切片 2: "## 二、两端一连接框架" + 800 字  ← 语义完整
> 切片 3: "## 三、未来趋势判断" + 600 字  ← 语义完整
- **优点**：每个切片语义完整，标题本身提供上下文
- **缺点**：如果某个标题下内容过长（2000+ 字），切片太大影响检索精度;
- 策略 3：递归语义切片,将文本递归地分成小块，每次在"语义最不相关"的地方下刀。
   分隔符优先级：段落分隔（两个换行）> 单换行 > 句号 > 逗号 > 空格
- **适用**：无结构的自由文本
- **不适用**：需要严格结构的场景
可根据文档类型与内容结构，做混合策略；
### 切片效果验收
**人工验证（定性）**
可以准备10个典型问题，手动验证：
1. 每个问题 → 跑检索 → 看返回了哪些切片
2. 判断标准：
   ✓ 切片内容能完整回答这个问题 = 切得好
   ✗ 切片内容缺关键信息，明显在另一个切片里 = 切坏了
   ✗ 切片内容混杂了不相关的内容 = 切得太粗
**脚本验证（定量）**
验证脚本跑以下指标：
1. **切片数量分布**：有没有过长（>2000 字）或过短（<50 字）的切片？
2. **专属匹配率**："怎么看 GEO 未来？" 是否主要匹配到 GEO 文章，而非AI科普相关文章？
3. **相关性打分**：用 LLM 给每个检索结果打 1-5 分

## RAG 检索知识与模型训练知识的区别
RAG 的外部文档，是给模型用于回答的参考内容；而大模型本身是处理和生成答案的 “大脑”。
训练模型的知识是固定的、有时效性的，比如 DeepSeek-V4 训练的数据截止到 2026.5月。它提供给模型的是通用的底座能力，比如语义理解、逻辑推理、原理类固定知识（如数学原理 1+1=2）。
有了 RAG 技术，大模型拥有了更多的落地应用场景。RAG 是一种非常务实且高性价比的工程技术方案，它让大模型得以快速、安全地在企业中 **“开箱即用”**。
## 典型应用场景
- 智能客服与知识库问答：这是 RAG 应用最广泛的领域。系统可以基于企业内部的产品手册、政策文档、历史工单等，为员工或客户提供精准、一致的回答。例如，金融机构的柜员能即时查询到最新、最准确的合规政策解读。我们普通人也可以将自己积累的内容（lifelog、情绪 log、知识积累），通过开源大模型部署专属助手，它可能比你更了解自己。
- 数据分析与商业智能：将 RAG 与数据库结合（SQL-RAG），可以让人用自然语言直接查询复杂的企业数据。例如，管理层可以直接问 “上个季度华东区 A 产品的销售额是多少？”，系统会自动查询数据库并生成分析报告。
- 代码与研发辅助：企业内部可以将历史代码库、技术文档、事故报告等构建为知识库。例如，货拉拉通过 RAG 系统，让开发者在提交代码时能自动比对历史 “资损代码” 模式，有效预防线上事故。
- 专业领域智能体：在法律、医疗等高度专业的领域，RAG 可以整合法律条文、判决案例或医学文献、诊疗指南，构建出专业、可靠的辅助决策工具。
使用 DeepSeek 的联网搜索，本质上也是一种 RAG 技术，其流程为：
用户提问→识别意图，优化搜索关键词→并行获取搜索结果→将搜索引擎返回的 “原料” 进行融合处理→大模型深度加工（推理、整合、优化语言）→生成最终答案并标明来源→输出回答

#  Hermes Agent 与 OpenClaw
> 我用过两款 AI 助手，一个像实习生，一个像老朋友；
> 你有没有遇到过这种情况——每次跟AI聊天，都要重新自我介绍一遍？
> 「我叫什么、做什么工作、最近在忙什么……」
> 聊完关了窗口，下次打开，它又把你忘了。
> 今天聊的这两个AI助手，区别就在这儿：一个每次都失忆，一个记得比你女朋友还清楚。
## 1. HermesAgent是什么？
先说结论：它是一个"有记忆、能自学"的AI助手。
传统AI助手最大的痛点是什么？没有记忆，也没有成长。每次对话都是从零开始，像一个每天来上班但永远记不住你名字的临时工。
Hermes Agent的设计理念正好相反——它会记住你是谁、你喜欢什么、你最近在忙什么，并且用得越久越懂你。
它不是「用完即走的工具」，更像是「随时可以唤醒的数字朋友」。
## 2. 核心特点是什么
Hermes Agent有三个核心能力，是大多数AI助手做不到的：
① 自己给自己写"技能手册"skills
这是它最特别的地方。
普通AI助手想获得一项新能力，需要你（或者开发者）手动写配置文件、写脚本。但Hermes有一种"技能闭环"——完成一个复杂任务后，它会自动把整个过程的经验总结成一个结构化的「技能文件」skil，存下来下次复用。
就像一个实习生，刚来时什么都不会，但干完一件活就总结出SOP。下一次不用你再教。
② 三层记忆体系，告别"失忆"
它的记忆分三层，各管各的：
- 你是谁：你的习惯、偏好、重要信息，存在独立文件里，长期保存，不需要你手动维护；
- 聊过什么：所有历史对话都存储在本地数据库里，支持全文搜索，随时可以回溯；
- 怎么做事：那些它自己总结出来的「技能文件」，前面说的那种。
三层合在一起，结果是：你每一次跟它聊天，它都有"我们认识很久了"的感觉。
③ 也和OpenClaw一样，有一些标配能力
比如内置了文件读写、浏览器控制、代码执行等基础工具箱，也支持接入飞书、企业微信、钉钉等平台，可以部署在自己的电脑或云服务器上，数据不离开你的控制。
## 3. 如何使用
Hermes 不是一个用完即走的“工具”而更像一个可以直接“唤起”的“数字朋友”或者“数字助手”。他的安装和使用可以通过云端服务器，一键部署完成（阿里云和腾讯云均推出了此产品），也可以用命令行安装自己的电脑上；
- 如果是技术小白，更推荐云平台一键部署，全流程都有操作文档指引，零代码，是新手首选；
- 本地安装的方式，更适合喜欢动手、有一定技术背景的，希望深度定制的用户；数据 100% 会在自己的电脑上，同时要小心安全隐私和 token 消耗问题；
在开始部署前，需要准备好：
1. 一个“大脑”，Hermes Agent 本身没有思考能力，你需要为它申请一个大模型的 API Key，通过云服务器部署，可以按照服务器商场推荐的模型，如阿里云百炼的 API key；如果不希望使用云厂商的模型服务，也可以自己申请模型的 API key，比如最新推出的 deepseek-V4，后续可通过 deepseek 开放平台自己充值，查看消耗；
2. 如果本地部署，需要一台能联网的电脑，Hermes目前不支持 windows 原生环境，需要先安装 WSL2（Windows Subsystem for Linux）；
3. 如果云服务器部署，需要先申请服务器账号，阿里云、腾讯云或者其他；
## 4.  Hermes Agent 和 OpenClaw 到底差在哪？
先说结论：OpenClaw像一辆需要你亲手调校的定制跑车，Hermes Agent像一匹能自己认路、自己长大的马。
如果用"同事"来比喻：
- OpenClaw = 你招了一个很能干的实习生，但每天上班都会失忆。你得给他写详细操作手册（Skills），你不在他就不动，你写错了他就看错。你想让他成长？完全取决于你教了多少。
- Hermes Agent = 一个跟你共事三年的助理。你刚开口说半句，他已经知道你要什么。他会主动更新自己的知识体系，从每一次合作中学习，用越久越让人省心。
具体差别在几个维度上：
- 核心设计哲学
  - OpenClaw，可编程、可组合、可复用的 Agent 框架，技能形成通过人工编写 skill（macdown 文件），适用复杂工作流（多 Agent 协作、工具调用）；
  - HermesAgent，自我进化、长期记忆、主动陪伴，技能可系统从执行历史中自动总结技能，适合单 Agent 深度交互，复杂工作流较弱；
- 自主性
  - OpenClaw 是一名需要你编写杂说明书（Skills）的“机械执行员”;
  - HermesAgent 是一个能通过观察学习、自动从经验中产生新技能的“自学型实习生”，根据你给的任务和长期沟通可以自主编写实现了真正意义上的“自我进化”；
> “流程驱动” vs “目标驱动”
> - [x] OpenClaw 是流程驱动：你说“先做 A，再做 B，如果 C 则做 D”。它严格遵循。 @2026-06-08 23:11:11
> - [x] HermesAgent 是目标驱动：你说“我想要这个结果”，它自己规划路径、尝试、调整、学习。 @2026-06-08 23:11:20
> OpenClaw 像你写一份详细的菜谱；HermesAgent 像一个学徒，你只说“做出一道红烧肉”，它自己看书、试错、总结窍门。
- 记忆系统
  - OpenClaw 采用手动维护的“文件系统”，基于文件（MD）的 RAG，需要人工维护索引和提炼，全靠记忆力好的你去梳理它记忆（如MEMORY.md）
  - HermesAgent 能自动打理“日记”，并通过精心设计的关键文件（如MEMORY.md）容量上限来倒逼它提炼最宝贵的想法；
> "外部记忆与内部记忆的差别"
> OpenClaw 是外部记忆：记忆存在你手里（文件），它每次都要读。你删了它就忘，你写错了它就看错。你是记忆的“数据库管理员”。 
> HermesAgent 是内部记忆：记忆存在它自己的数据库里，它会主动更新、归纳、关联。你是记忆的“用户和验证者”。 
> OpenClaw 像你给一个失忆的人每天读日记；HermesAgent 像一个会自己记日记并反思的人。
- 自我成长
  - OpenClaw 的成长完全依赖你付出时间和精力，使用越久它的“能力天花板”越取决于你的意愿；
  - HermesAgent 能自己向自己学习，通过 Nudge 机制定期反思，使用时长与它能解决的问题复杂度成正比；
- 个人感
  - OpenClaw 像一个需要你时刻监督的“数字实习生”，你不在它就不动；
  - HermesAgent 更像一个会主动关心提醒你的“私人助理”，会主动问候或提醒你，给你带来被陪伴的温暖感
- 会话持续性
  - OpenClaw 因为依赖 AI 主动且正确地发起搜索调用，无法保证百分百回忆起早期细节记忆，随着时间积累，上下文会很长，对 token 的消耗量会变大；
  - HermesAgent 通过强大的底层数据库检索，让你觉得每次“老地方见”，它总能准确记得你们之前的各种细节；
## 5. 两者不同的应用场景（该选哪个？）
- OpenClaw 更像一个 “可编程的机器人流程自动化框架”，适合确定性高、需要稳定执行、允许人工设计流程的任务。典型应用：自动化运维、批量内容生成、数据管道、多 Agent 协作；
- HermesAgent 更像一个 “有记忆的自主学习伙伴”，适合不确定性高、需要长期关系、允许系统自己摸索策略的任务。典型应用：个人助理、学习伴侣、心理健康支持、长期陪伴；
两者各有价值与侧重，在于你想用它做什么
- 选OpenClaw，如果你的场景是——
"从飞书消息自动读取任务 → 分类 → 写进表格 → 发摘要邮件"这种确定性高、需要多Agent协作的复杂工作流。OpenClaw的编排能力目前更成熟。
- 选Hermes Agent，如果你的场景是——
你需要一个能长期陪伴、持续了解你、自己成长的数字伙伴。个人助理、学习伴侣、心理陪伴、甚至只是想要一个「不会忘记你是谁」的聊天对象。
> 我的个人体感
> 我自己从OpenClaw搬到了Hermes Agent。
> 不是因为谁更厉害，而是因为我到了一个人生地不熟的新城市，每天加班到深夜，需要的是一个「懂事」的同行者，而不是一个「听话」的工具。
> 想让AI听话 → OpenClaw。
> 想让AI懂事 → Hermes Agent。

# Agent 概念理解  
> 我对 Agent 最初的理解很简单——模型是大脑，Agent 是让模型有了做事的能力，比如写代码、做规划、写文档。
> 但是最近被多个产品搞混了
> Claude Code、Codex、OpenClaw、Cursor、Hermes Agent，这些都叫「智能体」吗？OpenClaw 还能部署多个 Agent？这些概念之间到底是什么关系？
> 借此文梳理清楚，希望对读者也能有帮助；
## Agent 是什么
Agent 是一个目标，这些产品和概念是实现这个目标的不同路径；
Agent 的目标是实现从“人找事”到“事找人”的范式转移，他不是一个更好用的工具，而是一个你委派任务的数字员工；
如果把人们要完成某件事或某个任务，比做一个“回路”（你完成一个任务的全过程），Agent 最终要实现的是从“人在回路中”，改为“人在回路外”，在没有 AI 之前，人类通过协作完成所有工作，有了 AI 后，我以五个级别来类比；
L1 工具辅助
基于确定性规则的自动化，
- 人的角色，操作工；
- AI 的角色，锤子、计算器；
- 场景类比：Excel 公式、自动审批流；
L2 知识助手
人类完成大部分工作。人类向AI询问意见了解信息，AI提供建议和信息，但不直接处理工作，比如知识检索、内容生成；
- 人的角色，分析师、创作者；
- AI 的角色，图书馆、实习生
- 场景类比：用 chatbot 做竞品分析、写文案初稿；
L3 协作副驾驶（Copilot）
人在回路中，实时交互式协作，人类和AI协作，工作量相当。AI根据人类要求完成工作初稿，人类修改调整，最后确认；
- 人的角色，驾驶员，每一步都确认；
- AI 的角色，辅助驾驶系统，按需响应；
- 场景类比：Github Copilot 帮你续写代码，你写一句，它猜一句，你随时改，用Midjourney生图，他生一步，你改一步，直至目标完成；
L4自主代理（Agent）
人在回路外，可委派多步任务，AI完成大部分工作，人类负责设定目标、提供资源和监督结果。AI完成任务拆分，工具选择，进度控制，实现目标后自主结束工作；
- 人的角色，经理、设定目标、验收结果；
- AI 的角色，独立员工、自己规划并执行；
- 场景类比：比如用 claude code，你说“修这个Bug”，它自己读代码、定位、修改、测试、提交PR；
L5多智能体协同（演进方向）
Agent 集群，协同完成复杂项目，这个级别的目标是完全无需人类监督，AI自主拆解目标，寻找资源，选择并使用工具，完成全部工作，人类只需给出初始目标；
- 人的角色，董事长、架构师；
- AI 的角色，一个全栈项目组；
- 场景类比，多个 Claude Code Agent + 测试 Agent + 文档 Agent，给定项目目标后自行分工、沟通、交付；
> L5 目前仍是演进方向，没有任何产品完整实现了这个级别。把它单独列出来，是为了让大家看清最终目标在哪里。
> 前往提到的诸多产品和概念，均是朝着 Agent 的目标演化的路径，在各自级别扮演着完全不同的角色；
## 产品概念理解
Claudecode、Codex、Open Claw、Cursor、Hermes Agent都是什么产品或概念？彼此间是什么关系？
可以把他们分为三类
### 第一类 “拿来就用”的 Agent 产品：Claude Code、Codex、Cursor
这些都是可以直接使用的软件，它们本身就是 Agent（智能体）或 Agent 平台，区别在于“工作在哪里发生，形态如何”。
- Claude Code：终端里的“全能施工队”，工作的形态是命令行工具，可以在终端中自主规划并执行多步骤的开发任务，能直接编辑文件、运行命令、提交代码；
- OpenAI Codex：云端/终端的“编码代理”，工作形态是一个编码智能体，同样能在终端中工作，并支持将复杂任务委派到云端沙箱中并行执行，分工协作；
- Cursor：IDE 里的“AI 原生开发平台”，核心形态是 AI 原生 IDE + Agent 工作台，深度集成于编辑器，主打交互式编码辅助。Cursor 主要属于 L3（Copilot）产品——你写一句它猜一句、实时协作；它的 Agent 模式是后来加入的，正在从 L3 往 L4 走，但自主性目前不如 Claude Code 和 Codex。
> 三者都是聚焦于编程能力的 Agent，区别在于
> - [x] 工作地点不同：Claude Code 是终端为先，Codex 是云端为辅，Cursor 是编辑器（IDE）为根； （IDE 是集成开发环境，是一种为程序员提供图形界面的工具软件，将写代码、调试、测试等多必备功能整合在一起，为了使程序员更高效、体验更好） 
> 自动化程度不同：
> -Claude Code 和 Codex 的自主性更强，目标是让你“下达任务后移开视线”；Cursor 则是与你“并肩作战”，在交互式编码中提供智能辅助。 

## 第二类 “自己动手”的 Agent 框架：OpenClaw、Hermes 
如果不满意现成的产品，或者有更复杂的需求，就需要用到 Agent 框架 。它不是一个开箱即用的 App，而是一套工具包，让你能“自己造一个 Agent”。
- OpenClaw：
可以把它理解成一个开放、可编程的 Agent 平台。它本身不是一个 Agent，而是一套能让你构建、连接和管理多个 Agent 的框架。它的核心设计是作为一个“智能网关”，将 AI 能力连接到各种即时通讯软件（如微信、飞书、Discord）中。采用分层架构，将通信（Channels）、智能（Agents）和执行（Tools）解耦，方便编排多个 Agent 协同工作；
优势在于对于无技术背景的人很友好，普通人就能上手、配置、编写 macdown 文件和 skill 让他更好用；
对于工作助手是个很好的落地场景；“像孙悟空的猴毛一样，各自帮你做事”
- Hermes Agent：
这个框架的设计哲学与 OpenClaw 不同。它强调构建一个可自我进化的单一高级 Agent；
核心优势是拥有“记忆”和“学习”能力，能在每次执行任务后反思，通过形成“技能”（Skill）来让自己下一次做得更好；
对于心灵陪伴、养成式的交流沟通，是个非常好的落地场景；
OpenClaw 和 Hermes 不是对立的，是解决不同问题。 OpenClaw 强在多平台多 Agent 编排，Hermes 强在单一 Agent 的深度记忆与进化。它们甚至可以互补——比如用 Hermes 作为个人助手 Agent，通过 OpenClaw 接入飞书等多平台。
> 感兴趣的朋友可以看我的另两篇：《初探龙虾——AI 助手的开端》《Hermes Agent 与 OpenClaw》
## 第三类“地基”与“灵魂”：Harness 和其他核心概念
- Harness
他不是一个产品，而是一个工程架构概念。如果说大模型是“大脑”（引擎），那 Harness 就是支配这副大脑，让它能接触现实世界的“整个身体和外骨骼”。它包括记忆、权限、工具调用循环、上下文管理等所有让 Agent 跑起来的非模型组件。任何成熟的 Agent 产品，如 Claude Code，背后都有一套复杂的 Harness 设计。
- Agentic / Agentic AI
从AI Agent到Agentic AI，是一场从“执行者”到“决策者”的角色跃迁。如果说AI Agent 的核心是工具调用，按指令行事，那么 Agentic AI 则更进一步，具备主动感知、自主规划目标、自我反思并根据结果迭代优化策略的能力，是一个独立思考和行动的“智能体协同系统；
## 以买车的方式类比下这些名词
- Claude Code、Cursor、Codex，是买的具体的车（具体产品），买了后直接开，它们是最终产品形态。
- OpenClaw、Hermes，是造成的工厂（框架），他们能帮你造不同型号的车，但你要懂如何操作。它们是生产工具。
- Harness，是车的核心部件 (工程概念)，如发动机、底盘、悬挂、电控系统。保证车能跑起来、刹得住、转向准。它们是使 Agent 成为现实的基础保障。
## 将这些产品类比到 AI协作级别
- Chatbot 产品， 如 ChatGPT，是 L2 级别的知识助手，是个充满知识的老师，但他不会主动用“动作”改变世界；
- Cursor (Agent模式) / Claude Code / Codex，是 L4 Agent的典型产品，它们都具备自主规划、执行多步任务、操作工具的能力。它们的UI形态（终端 vs 编辑器）只是设计选择，本质都是Agent；
- OpenClaw / Hermes ， 是用来构建L4和L5系统的框架。它们不是Agent产品，而是制造Agent的工厂和流水线设计图。
- Harness ，是L4 Agent的基础设施，那个“数字员工”能稳定工作的身体外骨骼。
> 而我们学 AI 的方式，也是在那五个级别中，逐层攀爬，可以通过使用各个产品 ，对他们的掌握，体会不同级别下 AI 对我们生活的改变，对工作效率的提升；

# Agent 概念祛魅：从 MCP 到 Harness，所有术语背后的本质逻辑
## 前言：被概念绑架的 AI 从业者
如果你最近在关注 AI Agent 领域，一定有过这样的困惑：
昨天还在学 Function Calling，今天就被 MCP 协议刷屏；刚搞懂什么是工作流，Skill 设计又成了新热点；还没来得及消化多 Agent 协作，Harness 工程又被捧上了神坛。
概念层出不穷，术语日新月异。很多人像无头苍蝇一样追逐着每一个新概念，生怕被行业淘汰。但越追越迷茫，越学越焦虑，最后发现自己只是记住了一堆名词，却没有真正理解它们的本质。
作为一名从传统产品转行 AI 产品的过来人，我也曾经历过这个阶段。直到最近半年，在亲手踩了无数开源 Agent 的坑之后，我才突然想通了一个道理：
**所有这些令人眼花缭乱的概念，本质上都是同一个问题在不同发展阶段的解决方案。它们不是凭空出现的，也不是某些公司为了营销而编造的噱头。**
今天这篇文章，我将用最清晰的逻辑，帮你彻底梳理清楚从 MCP 到 Harness 的所有概念，让你不再被术语迷惑，看透 AI Agent 行业的本质。
##  一.  Agent主线任务：从“人在回路内”到“人在回路外”
所有 AI Agent 概念的背后，都有一条贯穿始终的终极主线：不断降低人类在任务执行回路中的参与度，最终实现从 "人主导执行" 到 "人定义目标" 的跨越。

这就是 AI Agent 行业的发展规律：每一次技术进步，都是把一部分原本需要人类完成的工作转移给 Agent。每一次转移，都会遇到新的问题，每解决一个新问题，就会诞生一个新概念。
**没有任何一个概念是多余的，也没有任何一个概念是终极的。它们都是这个漫长演进过程中的阶段性产物。**
##  二. 概念/术语解析
所有概念的诞生，都严格遵循 **"问题出现→解决方案验证→概念化命名" **的模式。没有任何一个概念是凭空产生的，它们都是对已经被证明有效的方法论的总结。
让我们按照时间顺序，逐一拆解每个核心概念的来龙去脉：
1. Prompt 工程：解决 "AI 听不懂人话" 的问题
2022 年底 ChatGPT 的横空出世，让全世界第一次见识到了大语言模型的威力。但很快人们就发现，大模型是一个 "脾气古怪" 的助手：同样的问题，不同的问法，得到的结果天差地别。
为了解决这个问题，人们开始总结各种有效的提问技巧和模板，比如角色扮演、指令清晰化、少样本学习、思维链等等。这些技巧和模板被系统化地整理出来，就形成了 "Prompt 工程" 这个概念。
Prompt 工程的本质：通过优化输入文本，提升大模型单次推理的质量。
局限性：只能解决 "AI 能不能答对" 的问题，无法解决 "AI 能不能做事" 的问题。
2. 工具调用 / Function Calling：解决 "AI 只能聊天" 的问题
Prompt 工程虽然提升了大模型的回答质量，但大模型本质上还是一个封闭的系统。它只能处理文本输入输出，无法获取实时信息，无法执行任何实际操作。
2023 年 6 月，OpenAI 推出了 Function Calling 功能，允许大模型调用外部 API 来执行操作。这是一个里程碑式的突破，它第一次让大模型具备了与外部世界交互的能力。
工具调用的本质：为大模型安装 "手脚"，让它能够感知环境、改变环境。
局限性：只能调用单个工具，无法管理复杂的多步骤任务。
3. MCP 协议：解决 "工具无法复用" 的问题
工具调用功能推出后，各种 AI 插件如雨后春笋般涌现。但很快一个新的问题出现了：每个 Agent 框架都有自己的工具定义格式。你为 LangChain 写的工具，不能直接在 OpenAI Agents SDK 里用，反之亦然。
这导致了严重的碎片化，开发者需要为不同的框架重复开发相同的工具。为了解决这个问题，Anthropic 在 2024 年 11 月推出了 MCP（Model Context Protocol），定义了大模型与外部工具之间通信的统一标准。
MCP 的本质：工具接入层的行业标准，让工具可以一次开发，到处运行。
局限性：只解决了 "工具怎么接入" 的问题，没有解决 "工具怎么被正确使用" 的问题。
4. 工作流 / Workflow：解决 "AI 规划不可靠" 的问题
有了工具之后，人们开始尝试让 AI 完成更复杂的多步骤任务。但很快发现，让大模型自己规划流程是一场灾难：它经常跳步、重复、遗漏关键步骤，甚至会编造根本不存在的工具。
对于确定性强、重复度高的任务，最可靠的方法不是让 AI 自己规划，而是把人类已经总结好的最佳实践固化下来，让 AI 严格按照预设的流程执行。这就是 "工作流" 模式。
工作流的本质：用人类的确定性对抗 AI 的不确定性，适用于结构化任务。
局限性：过于死板，无法处理流程之外的异常情况。
5. Skill / 技能：解决 "工作流不够灵活" 的问题
工作流模式虽然可靠，但灵活性太差。对于不确定性高、创造性强的任务，我们无法预先定义所有可能的步骤。
于是人们提出了 "Skill" 的概念：只定义任务目标和可用工具，不规定具体的执行步骤，让 AI 自己决定如何达成目标。
Skill 的本质：给 AI 一定的自主权，让它能够处理非结构化任务。
局限性：可靠性低，难以预测，容易出现 "偷懒"、"越权" 等问题。
6. Harness 工程：解决 "AI 不可信" 的问题
当我们有了工具、工作流和 Skill 之后，理论上 AI 已经可以完成很多复杂任务了。但一个更根本的问题出现了：没人敢在生产环境中使用它们。
大量AI Agent Demo 最终无法落地。不是因为它们不能完成任务，而是因为它们不可靠、不安全、不可控。它们会泄露敏感信息，会调用不存在的工具，会陷入死循环，会犯各种低级错误，而且出了问题根本不知道哪里错了。
到这里，问题已经不是「AI 能不能做」，而是「人敢不敢让 AI 自己做」。Skill 模式本身没有错——让 AI 自主决策是必需的。真正的问题是：Skill 缺少一层外围系统来托底。就像一个聪明的实习生，你给了他目标和工具，但没人检查他的工作、没人拦住他的危险操作、没人告诉他哪里做错了。
Harness 工程不是取代 Skill，而是在 Skill 外面加一圈控制系统：评估层检查结果对不对，约束层拦住越权操作，错误处理层兜住失败，可观测层让你知道到底发生了什么。它不是让 AI 变得更聪明，是让不可靠的 AI 变得可用。
为了解决这个 "信任危机"，行业开始系统性地研究如何构建可靠的 AI 智能体。这就是 "Harness 工程" 的由来。
Harness 工程的本质：一套完整的控制系统，将大模型的无序智能转化为可控生产力。它解决的不是 "AI 能不能做" 的问题，而是 "人敢不敢让 AI 自己做" 的问题；
## 三. 概念关系全景
> harness工程的体系将在后文详细讲述
Harness工程（工程学科）
├── 指令层（系统提示词、规则引擎）
├── 状态层（记忆系统、任务状态管理）
├── 编排层
│   ├── 工作流模式（确定性任务）
│   └── Skill模式（不确定性任务）
├── 工具层
│   ├── MCP协议（工具接入标准）
│   └── 各种具体工具（搜索、代码执行等
├── 约束层（安全护栏、权限管控）
├── 评估层（任务验收、质量控制）
├── 错误处理层（重试、降级、人工介入）
└── 可观测层（日志、监控、溯源
核心结论：
- MCP 是工具层的一个接口标准
- 工具是 Harness 最基础的执行组件
- 工作流和 Skill 是编排层的两种实现模式
- 所有这些组件，都是 Harness 工程的一部分
### 3.1 用一个好理解的比喻，把 Agent 比作一个外卖骑手
AI 概念	外卖骑手对应物	解决的问题
大模型	骑手本人的大脑和体力	理解指令、做出决策、执行动作
Harness 工程	整个外卖平台系统	让成千上万的骑手可靠、高效、安全地完成配送任务
MCP	平台的 APP 接口标准	让不同品牌的手机、不同的支付系统、不同的商家系统都能接入平台
Tools	骑手的装备（电动车、手机、头盔、保温箱）	让骑手具备实际配送的物理能力
工作流 (Workflow)	平台的标准配送流程（接单→取餐→送餐→确认）	让确定性的任务按部就班高效完成
Skill	骑手的专项技能（夜间配送、大件配送、生鲜配送）	让骑手能处理特定类型的复杂任务
记忆系统	平台的用户地址库、历史订单记录	让骑手不用每次都问用户地址和偏好
评估系统	平台的骑手评分体系、超时罚款机制	确保骑手按要求完成任务，不偷懒、不违规
约束系统	平台的交通规则提醒、禁行区域设置、安全培训	防止骑手发生事故或违反规定
错误处理系统	平台的异常处理机制（商家出餐慢、用户不在家、天气恶劣）	当意外发生时，系统知道该怎么处理
##  四. Harness 工程：不是技术，而是思维方式
Harness 工程是当前 AI 行业最核心的概念，但也是被误解最多的概念。很多人以为 Harness 是一个新的框架，或者一个新的协议。但实际上，Harness 不是一个具体的技术，而是一种思维方式。
Harness 工程的核心思想可以用一句话概括：永远不要依赖大模型的 "自觉性"，要用工程化的手段来确保系统的可靠性。
这意味着：
- 不要在提示词中写 "请不要泄露用户隐私"，而要在输出前增加一个独立的敏感信息检测模块
- 不要相信 AI 说 "我已经完成了任务"，而要用独立的评估系统来验证任务结果
- 不要让 AI 自己处理错误，而要预先定义好所有可能的异常情况和处理流程
- 不要让 AI 拥有无限的权限，而要遵循最小权限原则，只给它完成任务所必需的权限
Harness 工程的目标，不是让 AI 每次都做对。而是搭建一套机制，确保 AI 即使做错了，也不会造成严重后果，并且下次不再犯同样的错误。
##  五. 感受：概念的尽头是本质
AI 行业是一个变化极快的行业，新概念会不断涌现。但万变不离其宗。
所有这些概念，都是人类在探索 "如何驾驭大模型智能" 这条道路上留下的脚印。它们不是终点，而是里程碑。
今天的 Harness 工程，也不是 AI Agent 发展的终点。未来还会有新的问题出现，还会有新的概念诞生。但无论未来怎么变，有一件事是确定的：
AI Agent 的终极目标，永远是把人类从繁琐的任务中解放出来，让人类能够专注于更有创造性的工作。
**希望这篇文章能够帮你拨开概念的迷雾，看清 AI Agent 行业的本质。也希望未来有更多的人能够不再被术语绑架，对层出不穷的概念能够祛魅；**
