一 . 为什么要做这件事？
一名传统产品经理希望拥抱 AI，希望不是止步于工作中AI 工具的应用，而是深入的使用 AI 做些事情
VibeCoding 是个好的切入点，希望借此深入了解 AI 的能力和边界，体会“人人都是程序员”的时代的到来；
之前我对 AI 时代的产品经理的理解是抓两头，一头看的是这个技术的边界，另一头看的是如何达到用户的预期，把两头无限拉近，从而达到一个PMF（product-market-fit 产品市场契合度）
对AI技术的理解，了解这个技术的能力边界、演化进展，简单说是能做什么、使用什么方式做、不能做什么；
另一头是需求，结合业务场景，对用户需求的洞察，需要满足什么、满足到什么程度，是否能跑通商业模型；（这一头是传统产品经理的优势）
因此萌生了通过 VibeCoding 做点什么的想法，先从入门级的个人网站入手，不涉及过于复杂的技术栈，整个过程会拆分为三篇文章；
第一篇（本篇）会介绍网站整体的框架结构
第二篇会介绍网站静态页部分（包括前端页面及后端管理平台）
第三篇会介绍网站上的分身 Agent ；
记录下来的目的不是为了写教程，而是复盘，把过程中自己学到的东西记录下来，也希望能对其他读者有收获；
二. 包含哪些东西
我拆分为三个部分
1. 个人网站的静态页，包含首页、关于（个人介绍）、项目经历、文章、联系我；
其中文章页，是我发布过的公众号及小红书文章，通过管理后台上传文章内容，调用 LLM自动解析标签、字数、摘要，发布到个人网站上；
2. 数字分身 Agent，基于 RAG 结构的 Agent
网页右上角一个聊天入口。点开，AI 基于我的真实经历回答问题。"你做过哪些项目""你怎么看 AI 产品经理""GEO 行业前景怎么样"——它都能聊。
不是客服机器人。是"我"——用第一人称，用我的思维框架，用我写过的文章和经历作为唯一知识来源。潜在合作伙伴、HR、读者，可以通过跟"我"聊天来了解我的专业能力和思考方式。
3. 管理后台，给自己做的工具页面
传文章：粘贴公众号文章 → LLM自动提取标题、摘要、标签 → 一键推送到线上， 并且此文章自动向量化存储，作为分身 Agent 的知识库；
调 prompt：在线编辑器，改完即时生效，不用登服务器改文件；
看日志：查看 Agent 和用户的对话记录，发现 Bad Case 后针对性优化；
三. 一个 PM 的"技术栈"：四个工具撑起整个网站
在做这个网站之前，我对"建网站"的认知是这样的：买服务器、买域名、配环境、学运维。每一步都是前置条件，起初觉得门槛有些高
做完之后发现：我一个服务器没买，一个域名没买，一分钱没花，网站也能跑起来。

靠的是四个工具。每一个都不是什么高深的技术，关键是——在动手之前，我根本不知道它们存在。
3.1 Claude Code  不写代码，用自然语言做开发
Claude Code 是一个 AI 编程工具。你用自然语言描述想做什么，它生成代码。网上关于 claudecode 的介绍有很多，这里不再赘述了。我想分享的是，他可以作为你的伴学助理，他能做的不只是 coding，对我来说，过程中要学到的东西远比做出网站的结果更重要。
所以我把我的诉求写到了claude.md 文件，要求三段式协作，每次coding 之前
1. 先讲宏观 — 做什么、为什么、整体步骤
2. 落地执行 — 解释每一步原理、背景、目的
3. 回顾总结 — 做了什么、学到了什么
这样每次改一段代码，都会告诉我"为什么这样写""这段逻辑是什么""这里有个坑要注意"。
整个网站、管理后台、Agent 后端，全部代码都是 Claude Code 写的。我没亲手写一行，但每一行在做什么我都理解——因为它会教。
这对想学 Vibe Coding 的 PM 来说，这一点比单纯写出代码更有价值。你像是在跟一个资深工程师结对编程——他写，你问，他答。你收获的不只是一个能跑的网站，还有对技术的理解。
3.2 GitHub：代码的"网盘 + 时光机"
代码写出来了，放哪？
之前我只知道 GitHub 是程序员用的，具体干嘛的一知半解。实际用起来发现，它没那么玄乎。
它首先是一个代码网盘。你把代码放上去，随时随地能取。云端存储，不会丢。
但它比网盘多了一个关键能力——版本管理。每次修改自动存档，随时可以回到历史任何一个版本。改坏了，一秒回退。就像飞书文档的"历史版本"，但更强——每次提交都有一条说明，你知道"谁在什么时候改了什么"。
它还是一个协作平台。别人可以看到你的代码、提修改建议。开源社区就是这么运转的——全世界的开发者共同维护一个项目，彼此之间可能根本不认识。
在这个项目里，GitHub 是整个网站的"源头"。所有代码、文章数据、知识库文件都放在上面。后面要讲的 Vercel 和 Render，都从 GitHub 取代码。
Git 的日常操作就三步：add（勾选要保存的文件）→ commit（拍个快照，写上说明）→ push（上传到云端）。
3.3 Vercel：把 GitHub 文件夹变成网站
代码存在 GitHub 上了，怎么让它变成一个别人能访问的网站？
在做这个项目之前，我以为答案是：买服务器 + 买域名 + 配 Nginx + 配 SSL 证书。一个域名几十到几百块一年，一台最低配服务器也要几十块一个月。还得会 Linux 命令行。
Vercel 告诉我：不需要这些。
你连接 GitHub 仓库，Vercel 自动读取里面的 HTML/CSS 文件，生成一个 xxx.vercel.app 网址。免费。自带 HTTPS。每次 git push，网站自动更新——你不需要登录任何服务器，不需要重启任何服务。推送即部署。
在这个项目里，Vercel 负责"前台"。四个模块中的前三个——展示页、文章列表、管理后台——都跑在它上面。
类比：Vercel 就像一个自动化的出版社。你把书稿（代码）放在 GitHub 上，它自动排版印刷（生成网站），还帮你配好了门牌号和防盗门（域名和 HTTPS 证书）。每次你修改书稿，它自动出第二版、第三版。你什么都不用管。
3.4 Render：让 Python 代码在云端跑起来
Vercel 管了静态页面，但数字分身 Agent 需要一个"后台"——它要接收聊天消息、检索知识库、调用 AI 模型、返回回答。这些逻辑需要一个一直在跑的程序来处理。
Render 就是干这个的。和 Vercel 一样连接 GitHub 自动部署，但 Vercel 管的是"静态页面"，Render 管的是"动态服务"——需要持续运行的程序。
免费额度：512MB 内存。跑一个轻量 Python 服务，个人网站完全够用。每次 git push，Render 自动重装依赖、重启服务。
在这个项目里，Render 负责"后台"。Agent 的聊天 API、知识库检索、Prompt 组装、DeepSeek 调用——全部跑在它上面。用户在网页上发消息 → 请求飞到 Render → Agent 处理 → 返回回答。
类比：Vercel 是"橱窗"——展示内容的。Render 是"厨房"——处理请求的。用户在聊天窗口发消息，橱窗把订单传到厨房，厨房做好菜，端回来。用户只看到橱窗，不知道厨房在哪。

四. 关于数字分身 Agent
Agent 是这整个项目里最复杂、也最有意思的部分。将在本系列的后续文章为大家展开介绍。
一句话解释：给LLM配了个档案室。每次回答问题前，先从档案室调出你的真实经历和文章，再基于这些资料回答。
本质是 RAG 的架构， 感兴趣的朋友，可以看在我的另一篇文章RAG是什么·有什么用途；
工作流程不复杂：用户提问 → 从我的知识库里检索相关内容 → 把内容和人格 Prompt 拼在一起 → 发给 DeepSeek → 返回回答。本质就是"让 AI 只看着你的材料说话"。

在做Agent 的过程中，我觉得很大的收获是，了解了“Eval评估体系”，传统产品质量的好坏通过测试，对于 AI 产品如何界定质量的高低，是否符合预期呢？感兴趣的朋友看下另外两篇文章AI 产品中的 Eval 评估体系是什么Eval 评估：如何定义问题集的评估维度这是我在做的过程中总结下来的；
五. 总结下我的收获
1. AI 时代产品经理是面向大模型做产品设计，课题是基于对需求和业务的理解，如何做好模型的引导；
传统产品PRD，用户画像、功能范围、交互规范、验收标准。PRD 写得好不好，开发交付差别很大；
AI 产品，不管是 Skill、还是 Prompt、还是 Harness 工程，本质上都是如何引导出LLM 有正确的理解和输出你想要的东西。
2. 理解技术边界是关键能力
知识库检索方式从 TF-IDF 换成了 Embedding？两者有什么区别，成本与效果见如何 balence，为什么不做成实时联网搜索？
每一个决策都不只是"技术选型"，是"产品权衡"——在资源约束下找到最优解。PM 不需要会写代码，但需要理解每种方案能做什么、不能做什么。
 3. 调 Agent = 调产品
出问题 → 定位根因（是检索没命中？知识库的切片有问题？是 Prompt 没约束住？是模型幻觉？）→ 改一个变量 → 跑评测验证。
不是"调提示词"——是产品迭代。我建了一套 25 道题的评测集，涵盖基础事实、经历细节、观点追问、边界拒绝、多轮对话。每次改 Prompt 后自动跑一遍，看哪道题掉分了，针对性修复。
4. Vibe Coding 的核心不是"写代码"
是"描述清楚你要什么"。技术细节 AI 帮你处理。但"做成什么样""解决什么问题""边界在哪"——这是产品经理的天然优势。
5. 在用 ClaudeCode 中的一点收获
Agent 产品中的.md文件本质都是Skill文档，比如Openlaw和Hermes的memorey.md、user.md，ClaudeCode的 claude.md，都是 Skill 的原理，我同样可以在 Claude 里建 memory 文件，user 文件；
本质上这些 Agent 都是同一个模式——把结构化的上下文注入到每次对话里；有两段结构
第一段是「静态注入」：这些 md 文件在会话启动时就被塞进 prompt 里，不用等用户问什么，他们是「底色」；
第二段是「动态路由->prompt 组装」: 用户 query 进来-> 模型判断意图 ->找到对应的 skill->skill 内容注入到 prompt 里->带着注入后的 prompt 调模型生成回答；
